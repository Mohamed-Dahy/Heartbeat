# Heartbeat

Uptime and latency monitoring for the major LLM provider APIs — OpenAI,
Anthropic, Groq and Mistral.

Heartbeat checks each provider on a schedule, records whether it answered and
how long it took, and serves the results as JSON and as a public status page so
you can see both the current state and the history.

> **Status: in progress.** The core app is finished: it checks four providers
> every 60 seconds on its own, stores the results, serves a status page, and
> exposes Prometheus metrics — all from one Docker container. Not yet deployed
> anywhere, and the monitoring stack itself (Prometheus, Grafana, alerts) is not
> set up. See [Roadmap](#roadmap) for what is and is not done.

---

## About this project

Heartbeat is built to be operated, not just written. The application itself is
deliberately small and conventional; the emphasis is on everything that
surrounds it — containerisation, automated testing and delivery, infrastructure
as code, metrics, alerting, and running the service on a real host behind HTTPS.

It is developed in explicit stages, from a single tested function through to a
deployed and monitored service, with each stage kept small enough to reason
about on its own. The [Roadmap](#roadmap) below tracks progress through those
stages.

## What works today

A service that checks OpenAI, Anthropic, Mistral and Groq every 60 seconds,
stores every result in SQLite, and serves a status page showing the current
state and recent history for each.

The page shows one card per provider — current status, latest response time, and
a strip of coloured blocks for the last 30 checks (green up, amber slow, red
down). It refreshes every 30 seconds, and says so plainly when it cannot reach
the backend rather than quietly showing stale numbers.

### Endpoints

| Route | What it does |
| --- | --- |
| `GET /` | The status page |
| `GET /api/status` | The latest result for each provider, from the most recent round |
| `GET /api/history` | Returns past checks, newest first |
| `GET /healthz` | Liveness check — answers instantly, touches nothing |
| `GET /metrics` | Prometheus metrics, in Prometheus' plain-text format |
| `GET /docs` | Interactive API docs, generated by FastAPI |

Checks run **automatically every 60 seconds** in the background, so
`/api/status` is a read, not a trigger — refreshing it does not cause a check.
Set `CHECK_INTERVAL_SECONDS` to change the interval.

`/api/history` accepts `?provider=openai` to filter and `?limit=100` to change
how many rows come back (1–500, default 50).

```jsonc
// GET /api/status
[
  {
    "provider": "openai",
    "url": "https://api.openai.com/v1/models",
    "status": "up",
    "response_time_ms": 761.3,
    "status_code": 401,
    "error": null
  }
]
```

All providers are checked concurrently, so one round takes about as long as the
slowest single check rather than the sum of them.

### How a result is classified

| Result | When |
| --- | --- |
| `up` | The server replied, in under 2000 ms |
| `slow` | The server replied, but took longer than 2000 ms |
| `down` | No usable reply (timeout, refused connection, DNS failure), or a 5xx response |

**A 401 counts as `up`.** Heartbeat sends no API key, so providers answer
"401 Unauthorized". That is a *success* for our purposes: the server was awake,
heard the request, and answered. The question being asked is "is this API
reachable", not "am I authenticated". A 5xx response, by contrast, is the server
itself reporting that it is broken — so that counts as down.

## Getting started

**Prerequisites:** Python 3.12 and git. Node 22 is needed to work on the status
page, and Docker to run the container.

```bash
git clone https://github.com/Mohamed-Dahy/Heartbeat.git
cd Heartbeat
```

Create and activate a virtual environment:

```powershell
# Windows / PowerShell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
```

```bash
# macOS / Linux
python3 -m venv .venv
source .venv/bin/activate
```

Install the dependencies. Use the `-dev` file if you intend to run the tests:

```bash
pip install -r requirements-dev.txt
```

### Running the tests

```bash
pytest -v
```

Expected output: **12 passed**. The tests make no real network calls — outgoing
HTTP is intercepted by [respx](https://lundberg.github.io/respx/) and answered
with fixed responses, so the suite is fast and cannot fail because a provider is
having a bad day.

### Running the server

```bash
uvicorn app.main:app --reload
```

Then open <http://127.0.0.1:8000/api/status> in a browser. The database file
`heartbeat.db` is created automatically on first start.

### Running the status page (development)

Two terminals. The backend:

```bash
uvicorn app.main:app --reload
```

The frontend:

```bash
cd frontend
npm install
npm run dev
```

Open <http://localhost:5173>. Vite forwards `/api` calls to FastAPI, so no CORS
configuration is needed on the backend.

### Running it in Docker

```bash
docker build -t heartbeat .
docker run -d --name heartbeat -p 8000:8000 -v heartbeat-data:/data heartbeat
```

Then open <http://127.0.0.1:8000> for the status page. One container serves both
the page and the API — the React app is built inside a throwaway first stage, so
no Node ends up in the shipped image (161 MB).

The `-v heartbeat-data:/data` part matters: a container's own disk is wiped when
it is replaced, so the database lives on a volume outside it. Set a different
location with the `HEARTBEAT_DB` environment variable.

Check it is healthy:

```bash
docker ps          # STATUS should read "Up (healthy)"
```

> If port 8000 is already taken by a local `uvicorn`, the container will appear
> to work while your requests actually reach the old process. Stop it first, or
> publish on another port with `-p 8001:8000`.

## Known limitations

- Every check opens a fresh HTTPS connection instead of reusing one. That
  handshake is most of the measured time, so the numbers describe our network
  path as much as the provider's health. Reusing connections would make them
  more honest, and would let the `slow` threshold come back down.
- The 2000 ms `slow` threshold is a judgement call, not a measurement. It was
  raised from 1000 ms after healthy providers were repeatedly flagged as slow.
- Metrics live in memory, so counters restart at zero on every deploy. Normal for
  Prometheus, but worth knowing before reading a graph.
- Running with multiple uvicorn workers would start one scheduler per worker and
  multiply the rows. Fine today (single worker), needs handling before scaling.
- Not deployed anywhere yet — it runs locally only.
